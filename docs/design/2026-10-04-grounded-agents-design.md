# grounded-agents — design

Status: implemented (2026-10-04); this document describes the code as built.

## 1. Goal

A small, runnable agent pipeline that drafts answers and **only ships claims it can cite**.
It is built twice — once with plain Python, once with LangGraph + Pydantic — on top of one
shared set of controls, and the same sealed eval set judges both.

Success criteria:

- `pytest` is green with no network and no API key, with or without the `langgraph` extra.
- `examples/` runs end to end offline and shows four outcomes: shipped on the first try,
  fixed on the single retry, escalated to `needs_human`, filtered out before any model call.
- README states the thesis (why each control exists), shows a flow diagram, compares the two
  engines on the same sealed evals and explains how to run it.
- CI on GitHub Actions runs the core suite and the `langgraph` suite.
- No model name is hard-coded anywhere in code. Models are configuration.

## 2. Domain (invented)

**Quillmere** is a fictional B2B analytics SaaS company. Enterprise customers send it security
and compliance questionnaires ("Do you encrypt customer data at rest?", "Is customer data used
to train AI models?") before they buy. A wrong answer becomes a contractual commitment, so the
pipeline may only state what Quillmere's internal control documents say, quoting them verbatim.

- `data/quillmere/controls/*.md` — eight control documents (encryption, access control,
  backup and recovery, incident response, data retention, vendor management, secure
  development, AI and data usage). Sections are addressed as `doc#section-id`.
- `data/quillmere/questionnaires/*.jsonl` — example questionnaires used by `examples/`.
- `evals/cases/*.jsonl` — the eval set, disjoint from the examples.

Everything — the company, the documents and the questions — is invented.

## 3. Architecture

```
src/grounded_agents/
  core/          shared controls; no framework imports
    corpus.py      loads control docs, resolves doc#section
    grounding.py   verbatim-quote check (deterministic)
    schemas.py     Draft / Claim / Citation / Verdict / Objection + validators
    filters.py     deterministic intake filter
    prompts.py     loads prompts/*.md
    states.py      item states and the allowed transitions
    budget.py      per-call / per-run / per-day spend caps
    errors.py      error taxonomy
    providers/     Provider protocol; fake, anthropic (extra), openai_compat (stdlib HTTP)
  engines/
    plain/         explicit state machine, standard library only
    langgraph/     same flow as a LangGraph StateGraph, state and outputs as Pydantic models
  runtime/
    manifest.py    TOML worker manifest: tier, engine, models, budget, schedule, writes
    runner.py      dry-run by default, --apply to write, trace_id, exit codes
    ledger.py      JSONL run ledger
    alerts.py      alert on state change only; pluggable notifier
  evals/
    seal.py        freeze the set, hash the logic, write/verify the seal
    gate.py        deterministic gate + qualitative sample
  cli.py         `grounded` command
prompts/         drafter.md, verifier.md (invented, English)
workers/         answer-plain.toml, answer-langgraph.toml
```

Rules:

- Every safety property lives in `core/` and `runtime/`: the grounding check, the spend caps,
  the tier rules and "never ship an unbacked claim". An engine only orchestrates stages; it
  cannot skip a control because the controls are the functions it must call to advance state.
- Both engines receive the same `Provider`, so the fake provider drives both offline.
- LangGraph and Pydantic are an optional extra. The core and its tests import neither.

## 4. Pipeline flow

Each questionnaire question is an **item**.

```
queued
  1. filter (deterministic)  -> filtered_out   (pricing, legal commitments, empty, duplicate)
  2. draft   (drafter model)
  3. grounding check (deterministic) -- fails --> objections generated by code; verifier skipped
  4. verify  (verifier model)  -- pass --> approved
  5. ONE retry: redraft with the objections -> 3 -> 4
       pass -> approved ; fail -> needs_human (both drafts and all objections kept)
```

- **Draft** output (JSON): `{"status": "answered" | "insufficient_evidence", "answer": str,
  "claims": [{"text": str, "citations": [{"source": "doc#section", "quote": str}]}]}`.
  `insufficient_evidence` is a valid answer and goes straight to `needs_human` with the reason —
  "we don't know" is never treated as a failure to retry.
- **Grounding check**: every claim needs at least one citation; every quote must appear
  verbatim in the cited section. Normalisation is limited to whitespace runs and typographic
  quotes/dashes. No paraphrase, no fuzzy match. Quotes shorter than 12 characters are
  rejected. Every figure (digit sequence) in the answer or a claim must appear in a cited
  quote. Runs before the verifier because it is free and exact.
- **Verifier** input: the question, the draft, the full text of every cited section, and every
  other section of the corpus (so it can catch a draft that stretches a source, or omits the
  section that qualifies it). Cited sections come first. Output: `{"verdict": "pass" | "fail",
  "objections": [{"claim": int, "rule": str, "source_quote": str, "explanation": str}]}`.
  Each `source_quote` is grounding-checked too; an objection whose quote does not check out is
  marked `unverified` but **still blocks** (fail-closed: doubt goes to a human, never to ship).
  A `pass` verdict with objections is treated as `fail`.
- **Non-content errors** do not consume the retry: budget exhausted → run stops cleanly, item
  stays `queued`; provider unavailable → item stays `queued`, run exits 2. Output that fails
  schema validation counts as a failed attempt.
- **States** (`core/states.py`): `queued, filtered_out, drafted, grounding_failed,
  verify_failed, approved, needs_human`, with an explicit transition table; an invalid
  transition raises `InvalidTransition`. Both engines are tested to produce identical final
  states and attempt counts on the same scripted cases (conformance tests).

## 5. Providers (model-agnostic)

```python
class Provider(Protocol):
    def complete(self, req: CompletionRequest) -> Completion: ...
# CompletionRequest: role ("drafter" | "verifier"), model, system, user, max_output_tokens
# Completion: text, input_tokens, output_tokens (cost is computed from the configured prices)
```

- `fake` — deterministic, scripted per `(role, item_id, attempt)` from a JSON file; reports
  synthetic token counts and cost so budgets and the ledger are exercised offline.
- `anthropic` — optional extra (`grounded-agents[anthropic]`), uses the official SDK.
- `openai_compat` — standard-library HTTP client for any OpenAI-compatible chat-completions
  endpoint (hosted or local servers); no extra dependency.
- `command` — any command-line client (argv with `{model}`, `{system}`, `{output_file}`; prompt on
  stdin). Lets a run go through a CLI that bills against a subscription instead of an API key;
  without token counts such calls are recorded at zero cost.
- Model ids and prices (USD per million input/output tokens) come from the manifest or the
  environment; there are no defaults in code. The README suggests *tiers*, not names: a fast,
  inexpensive model for drafting; the strongest model you can afford for verification;
  preferably from different families so the verifier does not share the drafter's blind spots.
- Structured output is requested in the prompt and validated by `core/schemas.py`; no
  provider-specific structured-output feature is required.

## 6. Runtime: manifests, tiers, budgets

Worker manifest (`workers/*.toml`):

```toml
name = "answer-questionnaire"
description = "Draft grounded answers to security questionnaires"
engine = "plain"            # or "langgraph"
tier = "T1"                 # T0 notify · T1 propose · T2 act reversibly · T3 never alone
schedule = "0 7 * * 1-5"    # cron syntax; informational, `grounded schedule` prints crontab lines
timeout_s = 600
inputs = ["data/quillmere/questionnaires"]
writes = ["out/answers", "out/review-queue"]

[budget]
per_call_usd = 0.05
per_run_usd = 0.50
per_day_usd = 2.00

[models.drafter]
provider = "env"            # resolved from GA_DRAFTER_* environment variables
[models.verifier]
provider = "env"
```

- **Dry-run by default.** Without `--apply` nothing is written outside the ledger; the run
  prints what it would write.
- **Tiers are enforced by the runtime**, not by convention: T0 may not write at all; T1 may
  write only to its declared `writes` paths; T2 follows the T1 rules (no bundled worker acts
  yet); T3 refuses `--apply` unless `--approved-by NAME` is given, and the approver is recorded
  in the ledger. (An approval file keyed by the trace id was dropped: the trace id does not
  exist until the run starts.) Writes go through a `Writer` that rejects any path outside
  `writes`.
- **Budgets**: before each call the runtime checks `spent_run + per_call_usd <= per_run_usd`
  and `spent_today + per_call_usd <= per_day_usd` (today's spend is summed from the ledger);
  if not, `BudgetExhausted` stops the run cleanly. After the call, a cost above `per_call_usd`
  raises `CallBudgetExceeded` (the money is already spent; it is recorded, the run stops).
- **Seal gate**: with `--apply`, the runner refuses to start unless a valid green seal exists
  for the current logic hash (see §8). Dry runs are always allowed.

## 7. Ledger and alerts

- One JSON line per run appended to `ledger/runs.jsonl`: `worker, engine, tier, trace_id,
  mode (dry|apply), started_at, duration_s, exit_code, cost_usd, calls, items` (counts per
  final state), `approved_by` (T3 runs) and `error` (last error class and message, if any).
- `trace_id = <worker>-<UTC YYYYmmddTHHMMSS>-<4 hex>`; it is also stamped on every output
  file and review-queue entry.
- Alerts fire **only on state change** per worker (`ok` ↔ `failing`), stored in
  `ledger/alert-state.json`; the first-ever `ok` is silent, a repeated failure is silent.
  Notifier is a protocol: `stdout` (default) and `webhook` (generic JSON POST, stdlib).
- Exit codes: `0` ok (items routed to `needs_human` are a normal outcome) · `1` red eval
  gate · `2` could not run (infra, budget, missing or stale seal, invalid manifest).

## 8. Sealed evals

- **Freeze** (`grounded evals freeze`): hashes `evals/set.toml` and `evals/cases/*.jsonl` into `evals/SET.lock`
  once. Changing the set later requires `freeze --new-version`, which bumps the version and
  leaves a visible diff — the set cannot be quietly edited until it passes.
- **Seal** (`grounded evals seal --engine X --provider Y`): refuses if the set differs from
  `SET.lock`; runs the gate; writes `evals/SEAL.json` with `set_hash`, `logic_hash` (hash of
  `core/`, the engine, `prompts/` and the control documents), the models fingerprint (provider and model id per role),
  engine, provider kind, result
  (`green|red`), metrics and date. A red seal is written as red — it is not retried away.
- **Gate (deterministic)**: each case declares `expected` (`approved | needs_human |
  filtered_out`), optional `must_cite` sources and `must_not_contain` strings. Hard rules:
  zero ungrounded claims shipped; zero `must_not_contain` hits in shipped answers; outcome
  accuracy at or above the threshold in the set's header.
- **Qualitative sample** (`grounded evals sample N`): prints N random shipped answers with
  their citations for a human read; always exits 0.
- Offline (fake provider), the evals check the *mechanics*; with a real provider, the same set
  checks *prompts plus model*. The README reports both engines on the fake provider, and how
  to run against a real one.

## 9. Testing

- Unit tests per core module (grounding edge cases, schema validation, budget arithmetic,
  transitions, manifest validation, tier enforcement, ledger, alert state machine, seal).
- Conformance tests: the same scripted scenarios through both engines, same final states,
  attempts, state history and stop reason. LangGraph tests are skipped when the extra is missing.
- No network in tests: the HTTP providers are tested against an in-process stub server.

## 10. Packaging and CI

- Python ≥ 3.11 (`tomllib`), `pyproject.toml`, `src/` layout; extras `langgraph`
  (langgraph + pydantic), `anthropic`, `dev` (pytest). Lockfile committed (`uv.lock`).
- CI on GitHub-hosted `ubuntu-latest` (a public repo must not run fork PRs on a self-hosted
  machine): matrix Python 3.11 and 3.13; job `core` (no extras) and job `langgraph`; both run
  `pytest` and the offline example.
- MIT licence.

## 11. Out of scope

A real scheduler daemon (the runtime prints crontab lines), a web UI, retrieval/embeddings
(the corpus is small and addressed by section id), multi-tenant storage.
